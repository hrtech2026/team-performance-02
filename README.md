## Концепт

«Опора» помогает проверить договорённость о результате сложной работы, сохранив время сотрудника для глубокой задачи. Вместо счётчика активности используются заранее согласованные критерии, материал, отдельные блокеры и человеческий разбор; ошибки вывода можно исправить и оспорить.

Первый кандидат для проверки — продуктовая IT-команда. Применимость зависит от возможности согласовать результат и показать материал компетентному ревьюеру, а не от принадлежности только к IT. Смежная гипотеза текущего процесса — внутренняя юридическая служба; межорганизационная приёмка услуг — отдельное будущее расширение.

## Как работаем

Основная цепочка [C1–C3](docs/01_problem.md#next-iterations) дополнена [веткой B1–B3](docs/01_problem.md#development-branch), контрактом данных задачи D1–D5 и картой применимости. Последующие развилки — гипотезы развития, а не обязательства по выпуску продукта. Каждый участник добавляет собственное предложение и читает изменения своей зоны ответственности. Список кандидатов не подменяет голосование; отсутствие ответа не считается согласием.

Проверяем сильную текущую практику, организационные альтернативы и ручной процесс до автоматизации. Не утверждаем результаты интервью и пилота до их проведения. Публикуем изменения через отдельный Pull Request по этапу; последующие документы не сдаём как принятые только потому, что подготовлены их проекты.

## Сдача

[Задача первого этапа — Issue #2](https://github.com/hrtech2026/team-performance-02/issues/2).

1. Заполнить документ этапа и выполнить проверку `scripts/validate_docs.py`.
2. Создать Pull Request в main и дождаться «Проверка документов».
3. Для готового этапа оставить комментарий «Сдаю этап N»; замечания и вопросы фиксировать в Issue с прямой ссылкой на материал.
4. Соблюдать защиту ветки и требуемое ревью. Доску ведёт пульт автоматически по фактическим артефактам; вручную перемещать карточки не требуется. Зелёный CI проверяет форму, а приёмку определяет преподаватель.
