# Опора — требования

Требования выведены из [целевого процесса](03_tobe_architecture.md) и закрывают проблемы [AS-IS](02_asis_analysis.md#обнаруженные-проблемы). У каждой истории есть критерии приёмки, включая граничные и ошибочные сценарии. Связи сведены в [таблицу трассируемости](#трассируемость).

## User Stories

### US-01. Согласовать договорённость о результате

Как сотрудник, я хочу до начала работы согласовать с руководителем ожидаемый результат, критерии и контрольную точку, чтобы мою работу оценивали по результату, а не по видимой активности.

```gherkin
Given новая задача в трекере, When сотрудник и руководитель заполнили результат, от 2 до 5 критериев и дату контрольной точки и оба подтвердили, Then договорённость получает статус «активна» и версию 1
Given договорённость с одним критерием, When руководитель пытается её активировать, Then система не активирует её и просит добавить хотя бы ещё один критерий
Given сотрудник отклонил критерий с причиной, When руководитель не ответил 2 рабочих дня, Then договорённость эскалируется руководителю руководителя, а задача остаётся неактивной
```

### US-02. Изменить договорённость с историей

Как руководитель, я хочу менять критерии или срок только новой версией с причиной, чтобы задним числом нельзя было изменить то, по чему оценивают.

```gherkin
Given активная договорённость версии 2, When руководитель меняет срок и указывает причину, Then создаётся версия 3, версия 2 остаётся доступной только для чтения
Given изменение без причины, When руководитель сохраняет, Then система отклоняет изменение
Given ревью по версии 2 уже завершено, When создана версия 3, Then исход ревью остаётся связанным с версией 2
```

### US-03. Сообщить о блокере

Как сотрудник, я хочу отметить препятствие с владельцем зависимости в момент, когда оно возникло, чтобы руководитель помог сразу, а ожидание не считалось моим невыполнением.

```gherkin
Given активная договорённость, When сотрудник добавил блокер с описанием и владельцем зависимости, Then руководитель получает уведомление в течение 5 минут
Given открытый блокер, When наступила контрольная точка, Then блокер показывается в сводке отдельно от исхода по критериям
Given блокер без владельца зависимости, When сотрудник сохраняет, Then система просит указать владельца или пометить «владелец неизвестен»
```

### US-04. Получить сводку материалов по критериям

Как ревьюер, я хочу видеть по каждому критерию фрагменты материалов со ссылкой на источник, чтобы не тратить время на поиск и не запрашивать пересказ у сотрудника.

```gherkin
Given наступила контрольная точка и источники доступны, When система готовит сводку, Then по каждому критерию показан фрагмент со ссылкой на источник и версию или пометка «материал не найден»
Given модель вернула утверждение без ссылки на фрагмент входа, When сводка проходит проверку, Then утверждение удаляется, сводка помечается «требует ручной проверки»
Given источник недоступен или устарел, When наступила контрольная точка, Then формируется статус DATA_GAP, сводка не строится и отрицательный вывод запрещён
```

### US-05. Проверить сводку до решения

Как сотрудник, я хочу увидеть сводку раньше ревьюера и добавить своё пояснение, чтобы решение принималось по полным и верным фактам.

```gherkin
Given сводка готова, When сотрудник открыл её, Then он видит те же фрагменты и источники, что увидит ревьюер, и метку «подготовлено моделью» с версией
Given сотрудник добавил исправление, When ревьюер открывает материалы, Then исправление показано рядом с исходной сводкой
Given сотрудник не ответил 1 рабочий день, When срок прошёл, Then ревью начинается с отметкой «сотрудник не подтвердил», и это не считается согласием
```

### US-06. Принять решение по каждому критерию

Как ревьюер, я хочу ставить исход отдельно по каждому критерию и иметь возможность отклонить сводку целиком, чтобы решение было обоснованным и проверяемым.

```gherkin
Given материалы и сводка, When ревьюер выбирает исход по каждому критерию из «выполнен», «частично», «не выполнен», «нужно уточнение» и указывает источник, Then решение сохраняется, итоговый исход не вычисляется автоматически
Given ревьюер отклонил сводку, When он сохраняет решение, Then решение принимается по первоисточникам, отказ от сводки записывается в журнал
Given назначенный ревьюер не ответил 2 рабочих дня, When срок прошёл, Then задача переходит резервному ревьюеру; если его нет — статус «ожидает ревью» без исхода
```

### US-07. Оспорить решение

Как сотрудник, я хочу оспорить решение у человека, который его не принимал, чтобы ошибочный вывод можно было исправить.

```gherkin
Given решение по контрольной точке, When сотрудник подаёт обращение с причиной, Then назначается рассматривающий, не участвовавший в решении, и ответ приходит не позже 2 рабочих дней
Given обращение открыто, When другой процесс запрашивает исход, Then исход помечается «оспаривается» и не передаётся как окончательный
Given рассматривающий изменил исход, When решение сохранено, Then создаётся новая версия, прежняя остаётся в истории
```

### US-08. Улучшать процесс по агрегатам

Как руководитель команды, я хочу видеть агрегаты процесса M1–M4 без персонального рейтинга, чтобы улучшать процесс, а не сравнивать людей.

```gherkin
Given период 2 недели, When руководитель открывает отчёт, Then показаны M1–M4 по команде с числом случаев
Given в срезе меньше 5 человек, When запрошен отчёт, Then срез не показывается
Given запрос сравнения сотрудников между собой, When его отправляют через API, Then система возвращает отказ: такого отчёта нет
```

## Use Cases

### UC-01. Проверка результата исследовательской задачи

| Поле | Значение |
|---|---|
| Актёры | Сотрудник, руководитель, ревьюер, система Опора |
| Предусловия | Договорённость активна, указаны ссылки на материалы |
| Триггер | Наступила дата контрольной точки |

Основной сценарий:

1. Система проверяет доступность и свежесть источников.
2. Система готовит сводку по критериям со ссылками.
3. Сотрудник проверяет сводку и добавляет пояснение.
4. Ревьюер ставит исход по каждому критерию, указывая источник.
5. Руководитель и сотрудник согласуют действие: принять, доработать, снять блокер, новая точка.
6. Система записывает решение в журнал.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 1a | Источник недоступен или устарел (H5) | DATA_GAP, ручной режим, отрицательный вывод запрещён, уведомление владельцу интеграции |
| 3a | Сотрудник не ответил 1 рабочий день (H2) | Ревью по доступным фактам с отметкой «не подтвердил» |
| 4a | Ревьюер отклонил сводку (H3) | Решение по первоисточникам, отказ в журнале |
| 4b | Ревьюер недоступен 2 рабочих дня (H3) | Резервный ревьюер, иначе «ожидает ревью» без исхода |
| 5a | Результат отрицательный, но обоснованный | Критерий исследования считается выполненным, если вывод подтверждён материалом |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 2e | Сводка не прошла проверку схемы или содержит ссылку вне входа | Сводка отбрасывается, ревью вручную, событие в журнал |
| 6e | Журнал недоступен | Решение не сохраняется как окончательное, пользователь видит ошибку, повтор после восстановления |

Постусловия: исход по каждому критерию сохранён с источниками и хешем входа; следующая контрольная точка или закрытие задачи зафиксированы.

### UC-02. Согласованный результат не предъявлен

| Поле | Значение |
|---|---|
| Актёры | Сотрудник, руководитель, ревьюер |
| Предусловия | Контрольная точка наступила, источники свежие |
| Триггер | По всем критериям «материал не найден» |

Основной сценарий:

1. Система показывает «материал не найден» по критериям, без вывода о причине.
2. Сотрудник даёт пояснение или указывает блокер.
3. Ревьюер фиксирует исход «не выполнен» или «нужно уточнение».
4. Руководитель и сотрудник фиксируют конкретное расхождение, помощь и новую контрольную точку.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 2a | Подтверждён внешний блокер | Новая точка после снятия блокера, исход «нужно уточнение» |
| 4a | Повторное невыполнение после помощи | Руководитель передаёт кейс в отдельный человеческий процесс; система не делает вывод о намерении |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 1e | Ссылки на материалы не указаны | Система просит сотрудника указать ссылки до ревью |

Постусловия: расхождение, действие и новая точка записаны; санкций система не запускает.

### UC-03. Оспаривание решения

| Поле | Значение |
|---|---|
| Актёры | Сотрудник, независимый рассматривающий, владелец процесса |
| Предусловия | Решение по контрольной точке сохранено |
| Триггер | Сотрудник подал обращение |

Основной сценарий:

1. Система назначает рассматривающего, не участвовавшего в решении.
2. Исход помечается «оспаривается».
3. Рассматривающий изучает решение, источники и пояснение.
4. Рассматривающий подтверждает или меняет исход с обоснованием.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 1a | Независимого рассматривающего нет (H4) | Эскалация владельцу процесса, исход не используется до ответа |
| 4a | Срок 2 рабочих дня истёк | Эскалация владельцу процесса, уведомление сотруднику |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 1e | Повторное обращение по тем же основаниям | Отклоняется со ссылкой на ответ, новое обращение возможно при новых фактах |

Постусловия: исход подтверждён или исправлен новой версией, сотрудник получил ответ с основаниями.

## Нефункциональные требования

| ID | Категория | Требование | Проверяемость |
|---|---|---|---|
| NFR-01 | Производительность | Сводка по задаче с материалами до 50 страниц готовится не дольше 2 минут | Нагрузочный тест на 20 задачах |
| NFR-02 | Надёжность | При недоступности трекера или хранилища формируется DATA_GAP в течение 1 минуты, отрицательный вывод не создаётся | Тест с отключённым источником и таймаутом |
| NFR-03 | Надёжность | При недоступности модели процесс продолжается без сводки, ревью доступно вручную | Тест с отключённой моделью |
| NFR-04 | Безопасность | Модель работает внутри контура без сетевого выхода и инструментов | Проверка сетевых правил; попытка исходящего запроса из модели блокируется |
| NFR-05 | Безопасность | Права по ролям: сотрудник видит свои договорённости, руководитель — своей команды, ревьюер — назначенные | Отрицательные тесты доступа для каждой роли |
| NFR-06 | Приватность | Не собираются клики, клавиатура, снимки экрана, время в сети, личные сообщения, геолокация | Ревью схемы данных: таких полей нет |
| NFR-07 | Приватность | Срок хранения договорённостей и решений — 90 дней после закрытия последнего обращения, затем остаются только метаданные | Тест удаления с проверкой таблиц, индексов и кешей |
| NFR-08 | Объяснимость | Каждое утверждение сводки ссылается на фрагмент входа; утверждения без ссылки не показываются | Автоматическая сверка ссылок на наборе из 20 задач |
| NFR-09 | Аудит | Каждое решение пишется в журнал с `input_hash`, версией модели и источниками; журнал только дополняется | Попытка изменить запись журнала отклоняется |
| NFR-10 | Аудит | Доступ к журналу — у владельца процесса и рассматривающего обращения по назначенному кейсу; каждый просмотр и экспорт журналируются | Тест доступа и наличия записи о просмотре |
| NFR-11 | Затраты | Суммарное время сотрудника и руководителя на процесс не выше AS-IS; цель — сокращение не менее 20% | Дневник затрат в пилоте, метрика M1 |
| NFR-12 | Локализация | Интерфейс и сводка на русском языке, даты в часовом поясе пользователя | Проверка интерфейса и сводки |
| NFR-13 | Сопровождаемость | Сводку можно выключить флагом без остановки процесса | Тест переключения флага |
| NFR-14 | Телеметрия | Система считает по команде показатели своей работы: долю отклонённых сводок, утверждения без источника, время ревью со сводкой и без, частоту DATA_GAP, долю изменённых по обращению исходов; превышение порога создаёт уведомление владельцу процесса | Тест: искусственное превышение порога создаёт уведомление |
| NFR-15 | Надёжность ревью | Каждая пятая задача проверяется без сводки; исход «не выполнен» показывается резервному ревьюеру | Проверка маршрутизации на тестовом наборе задач |

## Ограничения и допущения

| Ограничение | Источник |
|---|---|
| Работодатель не вправе основывать решения, затрагивающие интересы работника, на персональных данных, полученных исключительно в результате автоматизированной обработки | ТК РФ, ст. 86 |
| Решения, порождающие юридические последствия для субъекта, на основании исключительно автоматизированной обработки запрещены без согласия | 152-ФЗ «О персональных данных», ст. 16 |
| Материалы работы и персональные данные не передаются во внешние API | Политика информационной безопасности, принятая в архитектуре TO-BE |
| Интеграция с трекером только на чтение | Архитектура TO-BE |

| Допущение | Кто подтвердит | Что меняется, если неверно |
|---|---|---|
| Для большинства задач можно сформулировать 2–5 проверяемых критериев | Руководители в пилоте на 20 задачах | Добавить тип «исследовательский вопрос» с одним критерием-вопросом |
| Обновление договорённости занимает не больше 10 минут в день | Дневник затрат | Сократить поля; при росте затрат выше AS-IS — отказаться от варианта |
| Есть компетентный резервный ревьюер | Руководитель команды | Увеличить интервалы контрольных точек или ввести выборочное ревью (R8) |
| Локальная модель находит фрагменты по критериям не хуже человека при меньшем времени | Сравнение на 20 размеченных задачах | Сводка остаётся выключенной, работает R0 |

## Definition of Ready

- [x] Пользователь и его роль определены
- [x] Ценность описана в одну фразу
- [x] Критерии приёмки сформулированы и проверяемы, включая граничные и ошибочные сценарии
- [x] Зависимости от других историй перечислены в трассируемости
- [x] Уровень автоматизации выбран и согласован с TO-BE
- [x] Понятно, где история создаёт риск для человека, и есть контрмера

## Definition of Done

- [ ] Реализация проходит все критерии приёмки
- [ ] Для L1 и выше существует лог решения с объяснением и источниками
- [ ] Есть тесты на граничные и ошибочные сценарии
- [ ] Права доступа настроены по ролям и проверены отрицательными тестами
- [ ] Документация для пользователя обновлена
- [ ] История просмотрена другим членом команды
- [ ] Риски ИИ для этой истории перепроверены, контрмеры работают
